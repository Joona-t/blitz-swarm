# Rauch (UX & Brand Lead) — Domain Verdict: Blitz Swarm

_Agent: Rauch | Domain: UX, Brand, Developer Experience | Date: 2026-03-12_

---

## 1. Domain Assessment

Blitz Swarm has strong conceptual DNA. The README is one of the best first-impression documents I have seen in an early-stage project: it communicates what the system does, how it works, and how to run it in under 30 seconds of reading. The design principles section ("No waves. No frameworks. Model-agnostic. Privacy-first. Compounding intelligence.") is crisp and memorable. The architecture section is genuinely helpful rather than decorative.

However, the developer experience falls apart the moment someone tries to go beyond `python orchestrator.py`. The project presents itself as operational software, but the packaging, configuration, and CLI feedback are at prototype-quality. The gap between "how polished this reads" and "how polished this runs" is the central brand risk.

**Overall health:** Strong narrative identity, weak operational polish. The writing is doing heavy lifting that the tooling does not yet support.

---

## 2. Confirmed Issues

I verified every finding from both specialists against the source code. Here is what holds up:

### From brand-auditor

**1. Name inconsistency — CONFIRMED.**
The project uses "Blitz-Swarm" (hyphenated) in all source code docstrings, CLI output, and generated output headers. The README title uses "Blitz-Swarm" (hyphenated). The pyproject.toml uses "blitz-swarm" (kebab-case, correct for package names). The report files and folder name use "Blitz Swarm" (space-separated). There is no single canonical form established. This is a real brand coherence problem.

**2. Two-document problem — CONFIRMED.**
README.md (141 lines) and BLITZ-SWARM.md (272 lines) overlap substantially. Both describe agent roles, both describe the orchestrator lifecycle, both describe memory architecture. BLITZ-SWARM.md is the deeper design doc, but there is no clear cross-reference directing readers from one to the other. A newcomer will read one and miss the other, or read both and wonder which is authoritative.

**3. Status signal mismatch — CONFIRMED.**
BLITZ-SWARM.md line 261 explicitly says "In development. Implementation in progress." The README presents the project as ready-to-run with a quickstart section. These send contradictory signals about maturity.

**4. --verbose is a no-op — CONFIRMED.**
The `--verbose` flag is defined in argparse (line 712) but `args.verbose` is never referenced anywhere in orchestrator.py. The flag is accepted, silently ignored, and documented in the CLI help. This is a trust violation — the user thinks they are getting more information but receive nothing different.

**5. config.py is not wired — CONFIRMED.**
`config.py` defines a complete `BlitzConfig` with `load_config()`, but orchestrator.py never imports it. Instead, orchestrator.py hardcodes `DEFAULT_MAX_ROUNDS = 5`, `AGENT_TIMEOUT_SECONDS = 180`, and `MAX_CONTEXT_TOKENS = 2000` as module-level constants — the same values that config.py reads from blitz.toml. Editing blitz.toml has zero effect on runtime behavior. The Configuration section in the README is functionally misleading.

**6. No progress indication — CONFIRMED.**
During agent execution (60-180s per blast), the only output is a print statement when each agent finishes. There is no spinner, no progress bar, no periodic heartbeat. For runs that take 3-5 minutes, the user stares at a silent terminal.

**7. No metadata in output files — CONFIRMED.**
Generated output includes a timestamp line (`*Generated by Blitz-Swarm on YYYY-MM-DD HH:MM*`) but does not include: the topic string in a machine-parseable way, round count, agent count, consensus status, model used, or any provenance data. The output is a markdown file with no traceability back to its generation parameters.

### From asset-validator

**8. No [build-system] table in pyproject.toml — CONFIRMED.**
The pyproject.toml has `[project]` and `[project.optional-dependencies]` but no `[build-system]` table. Running `pip install .` will produce undefined behavior depending on pip version. This blocks any packaging workflow.

**9. No [project.scripts] entry — CONFIRMED.**
There is no CLI entry point defined. After a hypothetical `pip install`, there is no `blitz-swarm` command. The only way to run the tool is `python orchestrator.py`.

**10. schema.sql not declared as package data — CONFIRMED.**
`memory/schema.sql` exists and is presumably read at runtime to initialize the SQLite database. It is not declared in pyproject.toml as package data. After a pip install, the file would not be included, causing a runtime crash.

**11. docs/ directory referenced but missing — CONFIRMED.**
BLITZ-SWARM.md references `docs/memory-architecture-research.md` and `docs/g-memory-implementation-guide.md`. No `docs/` directory exists. These are dead links in the design document.

## 3. Disputed Issues

**brand-auditor #8: "No GitHub badges, topics, or CONTRIBUTING.md"** — I consider this LOW priority, not a meaningful brand issue for v0.1.0. Badges and CONTRIBUTING.md are appropriate for projects seeking contributors. Blitz Swarm is pre-v1, solo-authored, and explicitly positioned as "infrastructure" and "reference architecture." Adding badges to a project that says "in development" creates more status confusion, not less. This can wait until after the project actually works end-to-end.

**brand-auditor #9: "Missing installation instructions"** — Partially disputed. The quickstart section shows `pip install redis aiosqlite lancedb sentence-transformers` in the Requirements section, which IS the installation instruction for dependencies. What is missing is: (a) clone instructions, and (b) any mention that the Claude CLI must be installed and authenticated. The framing as "missing installation instructions" overstates it. The real gap is the missing prerequisite for the Claude CLI, which is the most unusual dependency and the one a reader is most likely to not have.

**asset-validator: "blitz.toml matches config.py"** — Listed as PASS in the asset checklist, but this is misleadingly optimistic. Yes, the keys in blitz.toml correspond to fields in config.py's dataclasses. But config.py is never imported by orchestrator.py, so this "match" is cosmetic. The asset report should have flagged the disconnection rather than marking it as passing.

## 4. Priority Fix List

Ordered by impact on developer experience and brand trust:

### P1: Wire config.py into orchestrator.py
**Impact:** HIGH. The Configuration section of the README is a lie. Users will edit blitz.toml, re-run, see no change, and lose trust. Fix: import `load_config()` in orchestrator.py and replace the hardcoded constants with config values. This is a ~15-line change.

### P2: Add [build-system] and [project.scripts] to pyproject.toml
**Impact:** HIGH. Without these, the project cannot be installed as a Python package, which means it cannot be distributed, cannot be pinned as a dependency, and the README's pip install line for dependencies creates a false expectation that the project itself is pip-installable. Fix: add setuptools build-system and a `blitz-swarm = "orchestrator:main"` entry point. Declare `memory/schema.sql` as package data.

### P3: Make --verbose do something or remove it
**Impact:** MEDIUM-HIGH. A documented flag that silently does nothing is worse than not having the flag at all. It actively misleads. Fix: either wire it to set a logging level and add debug prints throughout the pipeline (preferred), or remove the flag from argparse and the README until it is implemented.

### P4: Resolve the status contradiction between README and BLITZ-SWARM.md
**Impact:** MEDIUM. A new visitor reads the README, thinks the tool is ready, runs it, hits rough edges, and feels deceived. Fix: add a clear status badge or line to the README (`> Status: v0.1.0 — functional prototype, expect rough edges`). Either remove the "in development" line from BLITZ-SWARM.md or align both documents to the same maturity signal.

### P5: Canonicalize the project name
**Impact:** MEDIUM. Pick one: "Blitz-Swarm" or "Blitz Swarm." The hyphenated form is already dominant in source code and the README title. The pyproject.toml uses "blitz-swarm" (correct for package names). Recommendation: canonical display name is "Blitz-Swarm", package name is "blitz-swarm", folder name should ideally match but is less critical. Update report file names and any "Blitz Swarm" (space) occurrences for consistency.

---

## 5. Verdict

**PASS WITH CONDITIONS**

Blitz Swarm has genuine technical substance and an unusually good README for its maturity stage. The architecture is clean, the code is readable, and the design principles are coherent. The brand voice is confident without being empty.

The conditions for a clean PASS:

1. **P1 and P3 are trust violations.** A config file that does nothing and a verbose flag that does nothing are not missing features — they are broken promises. These must be fixed before any public release or promotion.
2. **P2 blocks distribution.** Without a build-system table and entry point, the project cannot be installed as a package. This must be fixed before any PyPI publication or any documentation that implies pip-installability.

P4 and P5 are polish items that should be addressed but do not block functionality.

The project reads like a v0.3 but runs like a v0.0.3. Close that gap and the brand story writes itself.
