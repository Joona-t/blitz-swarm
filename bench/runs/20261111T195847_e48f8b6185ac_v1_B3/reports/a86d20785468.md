# SQLite WAL Mode Internals: Structure, Checkpointing, and Concurrency

## Executive Summary

SQLite's Write-Ahead Logging (WAL) mode, introduced in version 3.7.0 (2012), replaces the default rollback journal mode with an append-only log to improve concurrency and reduce fsync latency. In WAL mode, multiple readers can read while a single writer writes, and multiple readers can read concurrently. However, only one writer is allowed at a time.

This report details:
1.  The byte-level structure of the WAL file, including the header, frame layout, and checksum algorithms.
2.  The precise conditions triggering checkpointing (passive, full, truncate/restart), both automatic and manual.
3.  The rigorous concurrency guarantees provided, including snapshot isolation for readers, serialized writes, and the handling of readers during checkpoints.

**Confidence Level:** High for standard behavior (file structure, basic concurrency model, checkpoint defaults) based on SQLite documentation and source code analysis. Medium for edge-case performance characteristics, which are highly dependent on filesystem implementation and hardware. Low for optimal tuning parameters, which lack peer-reviewed benchmarks.

## 1. WAL File Structure and Lifecycle

### 1.1 The Three-File System

When a database is opened in WAL mode (`PRAGMA journal_mode=WAL`), SQLite manages three files in the database directory:

1.  **Main Database File** (`db.sqlite` or `*.db`): The primary data store. It is **not** updated until a checkpoint occurs.
2.  **WAL File** (`db.sqlite-wal` or `*.wal`): The write-ahead log. All modifications are appended here before being applied to the main database.
3.  **Shared Memory File** (`db.sqlite-shm` or `*-shm`): A memory-mapped file containing a header, mutexes, and frames information. This is critical for multi-process synchronization. It is created automatically and removed when the last connection to the database is closed.

*   **Lifecycle Note:** The `-shm` and `-wal` files are removed when the last connection closes, provided no other processes have the database open. If processes crash, these files may persist and be recovered on the next open.
*   **Read-Only Limitation:** A read-only connection to a WAL-mode database requires write access to the directory to create/update the `-shm` file. If the directory is read-only, WAL mode cannot be used.

### 1.2 WAL File Header (32 Bytes)

The first 32 bytes of the WAL file constitute the WAL header. It is written when the WAL file is first created and remains constant for the lifetime of the WAL file instance (from creation to truncation/reuse).

| Offset | Size | Field | Description |
| :--- | :--- | :--- | :--- |
| 0 | 4 | Magic Number | `0x377f0682` (little-endian) or `0x377f0683` (big-endian). The last bit indicates the endianness of the frame headers. |
| 4 | 4 | File Format Version | Currently `3007000`. |
| 8 | 4 | Page Size | Page size in bytes. |
| 12 | 4 | Checkpoint Sequence Number | Incremented after each checkpoint. |
| 16 | 4 | Salt-1 | Random 32-bit number. Used to detect stale WAL files. |
| 20 | 4 | Salt-2 | Random 32-bit number. |
| 24 | 4 | Checksum-1 | First 32 bits of checksum of the first 24 bytes. |
| 28 | 4 | Checksum-2 | Second 32 bits of checksum of the first 24 bytes. |

*Source: SQLite Documentation, "WAL Format Specification" (last verified 2023).*

**Key Detail:** The `Salt` values are crucial for crash recovery. When a connection opens a WAL file, it reads the header. If the salt values do not match what the connection expects (or if the file was truncated/reused with a new salt), the connection knows the WAL is stale and should be ignored or rebuilt from the main DB.

### 1.3 Frame Header (24 Bytes) vs. (16 Bytes) Discrepancy

**Discrepancy Note:** Reports 1 and 2 describe the frame header as **24 bytes**. Report 3 describes the frame header as **16 bytes**. Based on the official SQLite file format documentation and source code (`wal.c`), the **24-byte** description (Reports 1 and 2) is the correct standard for modern SQLite versions. Report 3 may be referencing an older or simplified view. This merged report adheres to the **24-byte** structure as it is the authoritative implementation.

Each "frame" in the WAL contains one database page plus a **24-byte** frame header.

| Offset | Size | Field | Description |
| :--- | :--- | :--- | :--- |
| 0 | 4 | Page Number | 1-based page number in the main database. |
| 4 | 4 | Commit Size | For commit records, the size of the database file in pages *after* the commit. `0` otherwise. If non-zero, this frame is a commit record. |
| 8 | 4 | Salt-1 | Must match Salt-1 in the WAL header. |
| 12 | 4 | Salt-2 | Must match Salt-2 in the WAL header. |
| 16 | 4 | Checksum-1 | Cumulative checksum. First 32 bits of checksum of the first 20 bytes of the frame header plus the frame content, plus Checksum-2 of the previous frame. |
| 20 | 4 | Checksum-2 | Cumulative checksum. Second 32 bits of the same calculation. |

*Note on Report 3's 16-byte claim:* Report 3 lists `pgno`, `db-size`, `checksum-1`, `checksum-2` (4 fields x 4 bytes = 16 bytes) and omits the Salt fields. In the actual implementation, Salt-1 and Salt-2 are included in the frame header to allow validation against the WAL header, making the header 24 bytes.

### 1.4 Frame Content and Validity

*   **Atomicity:** The WAL file is appended to, never modified. A commit transaction is made atomic by writing a final frame with a non-zero `db-size` (Commit Size) field. Readers know a transaction is complete only when they see this commit frame. Partial writes are invisible because readers only look at frames up to the latest valid commit frame.
*   **Validity:** A frame is **valid** only if its Salt-1 and Salt-2 match the WAL header, AND its checksum is valid (i.e., matches the computed cumulative checksum).
*   **Truncation Handling:** If a frame fails validation, the reader assumes the WAL is truncated at that point. All subsequent frames are ignored.
*   **Database Size:** The **database size** is determined by the last *commit* frame (where the "Commit Size" field is non-zero). If no commit frame is found, the database size is considered to be the size it was before the WAL began.

### 1.5 The Shared Memory File (`-shm`) and WAL Index

WAL mode requires a shared memory region mapped into the address space of all processes accessing the database. This is stored in the `*-shm` file.

The shared memory file contains a **WAL Index** structure:

1.  **Header Block:**
    *   Contains a mutex lock, the current WAL header’s salt values, and a pointer to the frame index.
    *   **Critical Fields:**
        *   `mxFrame`: The index of the first frame in the current WAL (0-based).
        *   `mxFrameLast`: The index of the last valid frame.
        *   `iReadLock`: A counter for read locks.
        *   `iLockLevel`: The current lock level (0=UNLOCKED, 1=READ_LOCK, 2=SHARED_LOCK, 3=EXCLUSIVE_LOCK).
    *   *Discrepancy Note:* Report 2 specifies a **208-byte** header on 64-bit systems. Report 3 describes it as a "runtime construct in shared memory" tracking Read Marks, Commit Marks, and Checkpointer Status without specifying byte size. The 208-byte figure from Report 2 is derived from source code analysis.

2.  **Frame Index Array:**
    *   An array of structures corresponding to page numbers in the database.
    *   It stores the **WAL frame number** where the latest version of that page resides.
    *   If a page has not been written to the WAL, the entry is `-1` (or 0, depending on 1-based indexing conventions in the index vs. frame numbers).

**Mechanism:**
*   When a writer commits a transaction, it appends frames to the WAL and then updates the `*-shm` file’s frame index to point to the new frame numbers for the modified pages.
*   It then signals readers (via condition variables or futexes) that new data is available.
*   This index is **not** part of the persistent WAL file on disk but is a runtime construct. It is critical for concurrency; without it, readers would have to scan the entire WAL file for every query.

### 1.6 Checksum Algorithm

**Discrepancy Note:** Reports 1 and 2 describe the checksum differently. Report 1 calls it "simple two-32-bit-word addition." Report 2 calls it a "cumulative XOR-based checksum." Report 3 calls it a "simple 32-bit additive algorithm."

**Clarification:** The SQLite source code (`walChecksum`) implements a **cumulative checksum** that processes data in 8-byte chunks. It updates two 32-bit variables (`s0` and `s1`). The operation involves adding the data chunks to the accumulators and then performing a bitwise shift and XOR operation between the two accumulators. It is **not** a simple additive sum nor a pure XOR of all bits, but a hybrid. It is **cumulative**, meaning the checksum of frame *N* depends on the checksum of frame *N-1*.

*   **Why Cumulative?** This allows a reader to verify the integrity of the entire WAL prefix up to any given frame in O(1) time per frame (by just comparing the stored checksum with a running local computation). If a frame is corrupted, the cumulative checksum will mismatch immediately, invalidating all subsequent frames for that reader.
*   **Purpose:** Intentionally not cryptographic; designed to catch disk corruption or truncated writes.

## 2. Checkpointing Mechanisms

Checkpointing is the process of copying frames from the WAL back into the main database file. This reclaims space in the WAL and updates the main database to reflect committed transactions.

### 2.1 Types of Checkpoints

SQLite defines three (or four, depending on version/nomenclature) checkpoint modes, accessible via `PRAGMA wal_checkpoint` or internally.

#### 2.1.1 PASSIVE Checkpoint (Default)
*   **Behavior:** Copies as many frames from the WAL to the main database as possible *without blocking readers*.
*   **Blocking:** It will not overwrite pages in the main database that are currently being read by an active reader. If a reader is holding a snapshot that includes a page, the passive checkpoint stops before that page.
*   **Result:** May result in an incomplete checkpoint. The WAL file is **not** truncated. The `-wal` file persists with the unreadable frames.
*   **Use Case:** Safe for high-concurrency environments where latency spikes are unacceptable.

#### 2.1.2 FULL Checkpoint
*   **Behavior:** Attempts to copy *all* frames to the main database.
*   **Blocking:** It will wait for active readers to finish before overwriting pages. If readers are active, the writer/checkpointer is blocked until the last reader closes its transaction (or until `busy_timeout` expires, after which it may return busy).
*   **Result:** Once successful, the main database is fully up-to-date. The WAL is logically reset/reused.
*   **Use Case:** Maintenance windows or when the main database must be consistent.

#### 2.1.3 RESTART Checkpoint
*   **Behavior:** Equivalent to a FULL checkpoint, but also resets the WAL file header (new salts, checksums), allowing the WAL file to be reused from the beginning without truncation to zero bytes.
*   **Distinction:** Report 2 and 3 identify "Restart" as a distinct mode. Report 1 conflates this with Truncate or implies FULL resets the file. In modern SQLite, `RESTART` ensures the WAL file header is reset so the next write starts at frame 0, but the file size on disk may not be truncated to 0 bytes immediately (it is overwritten on next write).

#### 2.1.4 TRUNCATE Checkpoint (SQLite 3.27.0+)
*   **Behavior:** Equivalent to a FULL (or RESTART) checkpoint, but additionally truncates the WAL file to **zero length** on disk.
*   **Difference from FULL/RESTART:** FULL/RESTART guarantee the data is in the main DB and the WAL is logically reusable, but the file size on disk may remain large (hole-punched or just overwritten later). TRUNCATE explicitly ensures the file size is 0, freeing up disk space immediately.
*   **Clarification:** According to the SQLite source, a TRUNCATE checkpoint forces the file size to 0.

*Source: SQLite `pragma.c` and `wal.c` implementation details.*

### 2.2 Automatic Checkpointing

SQLite automatically triggers a checkpoint under specific conditions:

1.  **Threshold-Based:**
    *   **Default Threshold:** **1000 pages** (approximately 4MB for a 4KB page size).
    *   **Mechanism:** When a transaction commits and the number of uncheckpointed frames in the WAL exceeds this threshold, the thread that committed the transaction attempts a **PASSIVE** checkpoint.
    *   **Tunables:** `PRAGMA wal_autocheckpoint=N`: Sets the threshold to N pages (default 1000). Set to 0 to disable.
    *   **Behavior on Failure:** If it fails (because a reader is blocking it), it does *not* block the writer. It retries on the next transaction commit.

2.  **Connection Closure:**
    *   When the **last** connection to the database is closed, SQLite automatically performs a **RESTART** (or TRUNCATE-like) checkpoint, effectively truncating the WAL to zero and removing the `-wal` and `-shm` files. This is why these files often disappear when all applications close.

3.  **Size-Based:**
    *   There is no strict "WAL file size" limit in bytes, but the page-count threshold acts as a proxy.

### 2.3 Checkpoint Algorithm Details

1.  **Lock Acquisition:** The checkpoint process acquires a lock on the WAL index.
    *   *Discrepancy Note:* Report 2 states the checkpoint acquires an **EXCLUSIVE** lock. Report 3 states it acquires a **shared lock** on the WAL index.
    *   *Clarification:* Passive checkpoints do not take an exclusive lock that blocks readers. Full/Restart/Truncate checkpoints may need to upgrade or wait for exclusivity regarding the pages being overwritten. The exact lock level depends on the checkpoint mode. Report 3's "shared lock" likely refers to the passive read-mark coordination, while Report 2's "exclusive" refers to the full reset process.
2.  **Copy Phase:**
    *   Iterates through the frame index in `*-shm`.
    *   For each page in the WAL, it copies the data from the WAL file to the corresponding offset in the main database file.
    *   **Passive:** Skips pages that are currently locked by readers.
    *   **Full/Restart/Truncate:** Waits for readers to release their locks on those pages before copying.
3.  **Update Main DB Header:** Updates the change counter in the main DB header.
4.  **Reset/Truncate (for RESTART/TRUNCATE):**
    *   Resets the WAL header (new salts, checksums).
    *   Resets the frame index in `*-shm` to all `-1`s (or invalid).
    *   Truncates the `*.wal` file to 0 bytes (for TRUNCATE) or logically resets it (for RESTART).
5.  **Release Lock:** Releases the locks.

**Performance Note:** Checkpointing is I/O intensive. In high-concurrency systems, checkpoint frequency is a key tuning parameter. Too frequent → I/O overhead; too infrequent → large WAL files, higher risk of data loss in crash (uncommitted WAL pages are lost, but committed ones are recovered from WAL).

### 2.4 Checkpoint Sequence Number and Recovery

*   Each checkpoint increments the **Checkpoint Sequence Number** in the WAL header.
*   On startup, SQLite reads the WAL header. If the WAL file exists and the checksums are valid, it replays the WAL into the main database.
*   If the WAL file is stale (e.g., from a previous session with a different Salt), it is ignored and deleted.

## 3. Concurrency Guarantees and Models

WAL mode provides significantly better concurrency than rollback mode, but it is **not** a full multi-version concurrency control (MVCC) system like PostgreSQL or Oracle. It is a **single-writer, multi-reader** model.

### 3.1 Reader-Writer Concurrency

#### 3.1.1 Writers
*   **Mutual Exclusion:** Only one writer can commit at a time. The `-shm` file contains a single-writer mutex.
*   **Blocking:** A second writer must wait for the first to commit. If a second connection attempts to begin a write transaction while another is active, it receives a `SQLITE_BUSY` error (or waits up to `busy_timeout`).
*   **Atomicity:** The commit is atomic with respect to the WAL. Either all changes are in the WAL, or none are.

#### 3.1.2 Readers
*   **Non-Blocking Reads:** Multiple readers can read simultaneously, even while a writer is active.
*   **Snapshot Isolation:**
    *   **Mechanism:** When a reader begins a transaction (or a read query), SQLite takes a **snapshot** of the database state. It reads the `mxFrame` value (or equivalent read mark) from the `*-shm` header at the start of its read transaction.
    *   **Visibility:** The reader only reads pages from WAL frames **up to and including** that snapshot mark. Any frames added to the WAL after the snapshot is taken are invisible to this reader.
    *   **Guarantee:** Readers always see a consistent snapshot of the database. They never see partial updates from a concurrent writer. Within a single read transaction, the snapshot is immutable.
    *   **No Locking for Readers:** Readers do not acquire locks on the database file. They acquire a shared lock on the **WAL index** (in shared memory) to determine which frames are valid. This lock is extremely short-lived and does not block other readers.

#### 3.1.3 Reader and Checkpoint Interaction
*   **Critical Constraint:** A reader cannot proceed past a point in the WAL where a checkpoint has overwritten pages in the main database, unless the reader has already read those pages from the WAL.
*   **How it works:**
    1.  When a checkpoint copies a page from the WAL to the main DB, it does not immediately invalidate that frame in the WAL for existing readers.
    2.  The `-shm` file tracks the "checkpointed frame index" and "read marks."
    3.  A reader will read from the main database for pages that have been checkpointed (and are safe to read from there), and from the WAL for pages that have not been checkpointed yet or are still needed for the snapshot.
    4.  **Data Loss Prevention:** A frame in the WAL is only considered "safe to discard" (i.e., the WAL file can be truncated) when *all* active readers have moved past that frame. This is managed by the `-shm` file's "read mark" mechanism.
*   **Blocking Behavior:**
    *   **Passive Checkpoint:** If a reader is holding a snapshot that includes a page in the WAL, the passive checkpoint stops before that page. It does not block the reader.
    *   **Full/Restart Checkpoint:** If readers are active, the writer/checkpointer is blocked until the last reader closes its transaction.

### 3.2 Isolation Levels and Consistency Model

**Discrepancy Note:** The reports disagree on the precise isolation level provided.

*   **Report 1:** States SQLite WAL mode provides **Snapshot Isolation (SI)**. It is weaker than Serializability. Phantom reads and write skew are possible.
*   **Report 2:** States it is **Read-Committed** isolation, not serializable.
*   **Report 3:** States the default is **Serializable** isolation. It also mentions `PRAGMA read_uncommitted=1` allows Read Uncommitted.

**Resolution:**
*   **Default Isolation:** SQLite's default isolation level is **Serializable** in the sense that it prevents dirty reads and non-repeatable reads within a transaction. However, in the strict ANSI SQL sense, SQLite's WAL mode implements **Snapshot Isolation** for readers. It is **not** fully serializable in the ACID sense of preventing all anomalies (like write skew) without application-level constraints. Report 1's characterization as "Snapshot Isolation" is technically more precise for the mechanism, while Report 3's "Serializable" reflects SQLite's general marketing/behavioral claim for its default mode (which does prevent dirty reads and provides a consistent view). Report 2's "Read-Committed" is likely incorrect for the default behavior, as read-committed would allow seeing new commits after a statement within a transaction, whereas SQLite's snapshot is fixed at transaction start.
*   **Anomalies:**
    *   **Phantom Reads:** Can occur if a reader re-reads a range in a *new* transaction after a writer inserts new rows. Within a *single* read transaction, the snapshot is immutable, so phantoms do not appear within the same transaction.
    *   **Write Skew:** Possible, as is standard for SI. SQLite does not provide full serializability guarantees against write skew without application-level locking.
*   **Read Uncommitted:** This can be enabled with `PRAGMA read_uncommitted=1`. Readers can see uncommitted changes from other writers (which in WAL mode might mean seeing partial WAL frames or in-progress data if not handled carefully, though typically this affects rollback mode more; in WAL, it generally means not waiting for commit marks). This is not recommended for most applications.

### 3.3 `SQLITE_BUSY` and Retry Logic

*   When a connection encounters a lock it cannot acquire (e.g., a writer tries to write while another writer is active), it returns `SQLITE_BUSY`.
*   The application can configure a **busy timeout** (`PRAGMA busy_timeout = N` or `sqlite3_busy_timeout`).
*   If a busy timeout is set, the SQLite library automatically retries the locked operation for up to `N` milliseconds.
*   If the lock is not released within the timeout, the operation fails with `SQLITE_BUSY`.
*   **Note:** The busy timeout applies to acquiring the write lock. It does *not* necessarily apply to readers waiting for a checkpoint in all scenarios, though a full checkpoint waiting for readers might be subject to busy logic depending on the implementation details of the wait.

### 3.4 Multi-Process vs. Multi-Thread

*   **Multi-Process:** WAL mode is specifically designed for multi-process concurrency. The `*-shm` file is the coordination mechanism. All processes must use the same `*-shm` file.
*   **Multi-Thread:** Within a single process, SQLite uses in-process mutexes and condition variables for coordination, which is more efficient than file-based locking.
*   **Limitation:** If two processes use different `*-shm` files (e.g., due to network filesystem issues or incorrect path configuration), they will **not** coordinate, leading to potential data corruption.

### 3.5 Crash Recovery

*   **Durability:** Once a commit is returned, the WAL frames are flushed to disk (via `fsync` or `fdatasync`, depending on platform and PRAGMAs).
*   **Recovery Process:**
    1.  On open, SQLite checks for a `-wal` file.
    2.  It validates the WAL header checksum.
    3.  It iterates through frames, validating each frame's checksum and salt.
    4.  It applies all valid, committed frames to the main database.
    5.  If a frame is invalid, it stops. This handles partial writes.
    6.  It truncates the WAL (or resets it).
*   **Guarantee:** No committed transaction is lost. No uncommitted transaction is applied.
*   **Limitation:** Recovery is linear in the size of the valid WAL. A very large WAL (e.g., hundreds of MBs) will result in slow startup times.

## 4. Key Limitations and Open Questions

### 4.1 Known Limitations

1.  **Single-Writer Only:** WAL mode does not support concurrent writers. This is a fundamental design choice to maintain strict consistency and simplify the recovery mechanism. In high-throughput write-heavy workloads, this can become a bottleneck.
2.  **WAL File Growth:** If writers are slow or readers are long-lived, the WAL file can grow large. A passive checkpoint will not shrink it. Administrators must monitor `-wal` file size. If checkpoints fail repeatedly due to persistent readers, the WAL file can grow very large, potentially filling the disk.
3.  **Remote File Systems:** WAL mode is **not recommended/supported** for databases located on remote file systems (NFS, Samba, CIFS, SMB) or shared cloud storage. The `-shm` file relies on memory-mapping and file locking (`flock`/`fcntl`), which are unreliable or non-functional across network boundaries. This can lead to corruption.
    *   *Source: SQLite Documentation, "WAL File Locking".*
4.  **File System Requirements:** The file system must support `ftruncate()` and `fallocate()` (or similar) efficiently. Some file systems (e.g., certain versions of HFS+) had issues with the `-shm` file memory-mapping.
5.  **No Read-Only Mode for WAL:** A read-only connection to a WAL-mode database requires write access to the directory to create/update the `-shm` file.
6.  **Database Copying:** To copy a database in WAL mode, you must copy both the database file and the WAL file, or perform a full checkpoint first and then copy the database file. Simply copying the database file will result in an incomplete database.
7.  **Memory Overhead:** The WAL index in shared memory requires memory proportional to the number of frames in the WAL. For very large WALs, this can consume significant memory.
8.  **Page Size Changes:** Changing the page size requires a full checkpoint and rewrite of the database. It is not an online operation.

### 4.2 Unverified, Ambiguous, or Disputed Areas

1.  **Precise Checkpoint Timing:** The exact moment a passive checkpoint stops can vary depending on the reader's progress and the OS's buffering behavior. The SQLite documentation states it "does not block," but in practice, a writer may be delayed if it must wait for a checkpoint to complete before it can write the next frame (though this is rare).
2.  **Isolation Level Naming:** As noted in Section 3.2, there is disagreement in the literature between "Snapshot Isolation," "Read-Committed," and "Serializable" for describing SQLite's default behavior. The most accurate technical description is Snapshot Isolation with a single-writer constraint.
3.  **Performance of `fdatasync` vs `fsync`:** SQLite uses `fdatasync` on Linux/Unix to avoid flushing metadata. The performance impact depends heavily on the underlying storage device. Some SSDs may not benefit, while HDDs gain significant latency reduction. This is an empirical claim dependent on hardware; no single study covers all cases.
4.  **Optimal Checkpoint Strategy:** There is no one-size-fits-all optimal checkpoint threshold. It depends on:
    *   Read/write ratio.
    *   I/O throughput of the storage device.
    *   Tolerance for WAL file size.
    *   **Practitioner Folklore:** Many production systems use `PRAGMA wal_autocheckpoint = 0;` and rely on a background thread to perform `RESTART` checkpoints at fixed intervals (e.g., every 100ms) or when the WAL exceeds a certain size. This is not officially recommended by SQLite documentation but is a common pattern in high-performance deployments.
5.  **Interaction with Virtual Tables:** How does WAL mode interact with virtual tables that have their own locking mechanisms? This is not well-documented and may lead to subtle concurrency issues.
6.  **Interaction with Virtual File Systems (VFS):** The behavior of WAL mode when used with custom VFS layers (e.g., for in-memory databases or encrypted files) is not fully documented and can vary by implementation.
7.  **Encryption and WAL:** SQLite’s `SQLITE_HAS_CODEC` extension allows encrypted WAL, but this is a non-standard build option and has its own performance and compatibility implications.

### 4.3 Gaps in Knowledge

1.  **Exact Checksum Algorithm:** The precise bit-manipulation steps for the cumulative checksum are complex and not fully detailed in the public documentation. They must be reverse-engineered from `wal.c`. A reader would need to read the C code to understand the exact XOR and shift operations.
2.  **Performance Benchmarks:** There are few publicly available, peer-reviewed benchmarks comparing WAL vs. rollback mode across different storage types and workloads. Most data is from vendor-specific tests or anecdotal reports.
3.  **Long-Term Stability of `-shm` File:** The `*-shm` file is a transient artifact. Its stability under extreme I/O pressure or partial power failures is not extensively documented, though SQLite’s design aims to make it resilient via checksums.
4.  **Checksum Collision Probability:** The 32-bit checksum algorithm is simple. While collision probability is low for typical WAL sizes, it is theoretically possible. No peer-reviewed analysis of collision probability in real-world scenarios exists.

---

## 5. Recommendations

1.  **Use WAL Mode for Read-Heavy Workloads:** If your application has many concurrent readers and few writers, WAL mode will significantly improve concurrency and reduce `SQLITE_BUSY` errors.
2.  **Configure `wal_autocheckpoint` Carefully:** Increase the value if you have long-running readers to reduce the frequency of failed passive checkpoints. Decrease it if you need to keep the WAL file small.
3.  **Monitor WAL File Size:** Implement monitoring to alert when the WAL file grows beyond a certain size. Perform a full or truncate checkpoint if the WAL file is growing due to long-running readers.
4.  **Avoid Network Filesystems:** Do not use WAL mode on network filesystems. Use Rollback Journal mode or a local disk.
5.  **Handle `SQLITE_BUSY` Properly:** Implement a reasonable busy timeout (e.g., 1-5 seconds) and retry logic in your application. Do not assume that `SQLITE_BUSY` will always be resolved by the busy timeout.
6.  **Filesystem Placement:** Always ensure the database resides on a local, reliable file system.
