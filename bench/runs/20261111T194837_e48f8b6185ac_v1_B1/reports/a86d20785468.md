# SQLite WAL Mode Internals: Structure, Checkpointing, and Concurrency

## Executive Summary

Write-Ahead Logging (WAL) is an alternative concurrency control mechanism for SQLite, introduced in version 3.7.0 (2012). It replaces the default rollback journal mode by moving write operations to a separate file (the WAL file) while the main database file is only updated during checkpoints. This design provides significant concurrency benefits, allowing readers to proceed while writers are active, and it decouples the physical update of the database file from the logical commit of a transaction.

This report details the internal structure of the WAL file and the accompanying shared memory file (WAL Index), the specific mechanisms and triggers for checkpointing, and the precise concurrency guarantees (isolation levels, locking behavior) provided by this mode.

---

## 1. WAL File Structure and Shared Memory

Unlike the default rollback journal, which records *original* page contents for potential rollback, the WAL file appends *modified* pages to a separate file. The database engine applies these pages to the main database file only during checkpoints.

To coordinate access between multiple processes, SQLite uses two auxiliary files:
1.  **The WAL File (`<database-name>-wal`):** Stores the committed pages.
2.  **The Shared Memory File (`<database-name>-shm`):** Contains the **WAL Index**, which tracks the current commit point and manages locking coordination.

### 1.1 The WAL Index (Shared Memory)

The WAL Index is a critical internal component stored in the `-shm` file. This file is accessed via memory mapping (`mmap`) if the operating system supports it, or via file locking as a fallback. It allows readers and writers to communicate without extensive file locking on the main database file.

The WAL Index primarily contains:
*   **The Current Commit Frame (`iFrame`):** A counter indicating the index of the most recent committed frame in the WAL. This tells readers where to stop reading when establishing a snapshot.
*   **Locking Primitives:** Mutexes and file locks used to protect the shared memory structure and coordinate exclusive access for writers and checkpoints.

**Clarification on Reader Tracking:**
Contrary to some assumptions, the WAL Index does **not** store an array of individual reader snapshots. Instead, it maintains a global state regarding the maximum frame number available. Readers do not register themselves with a unique ID in the WAL Index. Instead, a reader establishes a "snapshot" by reading the current `iFrame` value at the start of its read transaction. The safety of this snapshot (i.e., ensuring the WAL frames it needs are not overwritten or truncated) is guaranteed by the locking protocol on the `-shm` file and the main database file, not by an internal registry in the WAL Index. Specifically, writers cannot reset the WAL (via TRUNCATE checkpoint or restart) while any reader holds a read lock on the `-shm` file.

### 1.2 WAL File Header

The WAL file begins with a 32-byte header (8 words of 4 bytes each). This header is written when the WAL file is initialized or reset.

| Offset | Size | Field Name | Description |
| :--- | :--- | :--- | :--- |
| 0 | 4 | Magic Number | `0x377f0682` or `0x377f0683`. The LSB indicates the checksum byte order (big-endian `2` vs little-endian `3`). |
| 4 | 4 | File Format Version | Always `3007000`. |
| 8 | 4 | Page Size | Size of database pages (bytes). Must match the main database. |
| 12 | 4 | Checkpoint Sequence Number | Incremented when the WAL file is **reset** (e.g., after a TRUNCATE checkpoint or recovery). It is **not** incremented on every PASSIVE or FULL checkpoint. It serves to identify the specific "instance" or generation of the WAL file. |
| 16 | 4 | Salt-1 | Random number generated when the WAL file is created/restarted. |
| 20 | 4 | Salt-2 | Random number generated when the WAL file is created/restarted. |
| 24 | 4 | Checksum-1 | Cumulative checksum of bytes 0–15. |
| 28 | 4 | Checksum-2 | Cumulative checksum of bytes 0–27. |

**Header Persistence:**
The header fields (specifically the Salts and Checksums) remain constant for the lifetime of a WAL file instance. The header is only overwritten when the WAL file is **reset** (such as during a `TRUNCATE` checkpoint or crash recovery). During normal append operations, the header is not modified.

**Checksum Mechanism:**
The checksum is a specialized arithmetic checksum (FNV-1a variant) defined in `wal.c`. It is cumulative. The checksum stored in the header is the checksum of the first 16 bytes of the header. The checksums in subsequent frames are calculated based on the previous frame's checksum and the current frame's data.

### 1.3 WAL Frame Structure

Following the 32-byte header, the file consists of a sequence of **frames**. Each frame represents a single modified database page.

**Frame Header (24 bytes):**

| Offset | Size | Field Name | Description |
| :--- | :--- | :--- | :--- |
| 0 | 4 | Page Number | The page ID in the main database file (1-based). |
| 4 | 4 | **DB Size** | The size of the database in pages **at the end of the transaction** that this frame belongs to. |
| 8 | 4 | Salt-1 | Copied from WAL header. |
| 12 | 4 | Salt-2 | Copied from WAL header. |
| 16 | 4 | Checksum-1 | Cumulative checksum of the entire WAL file up to and including this frame header. |
| 20 | 4 | Checksum-2 | Cumulative checksum (second word) up to and including this frame header. |

**Frame Data:**
Immediately following the 24-byte frame header is the full content of the database page (e.g., 4096 bytes).

**Total Frame Size:** 24 + Page Size bytes.

**Checksum Scope:**
The checksum in Frame *N* is calculated over:
1.  The Checksum-1 and Checksum-2 from Frame *N-1*.
2.  The first 8 bytes of the current Frame *N* header (Page Number and DB Size).
3.  The full page data of Frame *N*.
*(Note: The Salt and Checksum fields themselves are not included in the input to the checksum calculation for the next frame, but the result is stored in the current frame.)*

### 1.4 Commit Records and Frame Validity

A critical distinction in WAL mode is how "commits" are identified.

*   **The `DB Size` Field (Offset 4):** The `iDbSize` field in a frame header indicates the size of the database in pages **at the end of the transaction** to which this frame belongs.
    *   If a transaction modifies 5 pages, all 5 frames will have the *same* `iDbSize` value in their headers, reflecting the database size *after* the transaction completes.
    *   If a transaction adds a new page, the `iDbSize` will be one larger than the previous transaction's DB size.

*   **Identifying a Commit Frame:**
    A frame is considered a "commit frame" (marking the end of a transaction) if it is the **last frame of a transaction**.
    *   In the WAL sequence, transactions are contiguous.
    *   The last frame of a transaction has a valid checksum and Salt values.
    *   The `iDbSize` in this frame reflects the final state of the database after the transaction.
    *   **Correction to Common Misconception:** You do **not** identify a commit frame by checking if the `iDbSize` matches the *next* frame's `iDbSize`. The next frame belongs to the *next* transaction and may have a different `iDbSize` (if the next transaction adds/removes pages) or the same (if it only updates existing pages within the same size limit). The commit boundary is determined by the logical transaction structure and the validity of the checksum chain. The reader knows a frame is a commit point if it is the last frame before the "current commit point" defined by the `iFrame` in the WAL Index, or during recovery, the last frame with a valid checksum before a gap or reset.

### 1.5 Recovery

If SQLite crashes mid-write, recovery involves:
1.  Opening the WAL file.
2.  Verifying the header (Magic Number, Salt, Checksum).
3.  Scanning frames sequentially, verifying cumulative checksums for each.
4.  **Stopping** at the first frame where the checksum fails, the Salt value mismatches the header, or the page number is invalid.
5.  Applying **only valid, committed frames** up to the last consistent commit point to the main database file.
6.  Uncommitted partial transactions are discarded because they do not form a complete, checksum-verified commit record.
7.  The WAL file is then reset (new salts, new checkpoint sequence number, empty frames) or truncated.

## 2. Checkpointing

Checkpointing is the process of applying changes from the WAL file to the main database file. Once all changes in the WAL are applied to the main database, the WAL file can be reused.

### 2.1 Types of Checkpoints

SQLite supports distinct behaviors for checkpoints, controllable via `PRAGMA wal_checkpoint`:

1.  **PASSIVE:**
    *   Applies changes to the main database only if no other processes are actively reading from the WAL.
    *   If a reader is present (holding a read lock on the `-shm` file), it stops immediately without applying all changes.
    *   **Non-blocking:** It does not wait for readers to finish.
    *   **Effect:** The WAL file size on disk does *not* change. The internal "checkpoint frame" advances, but the file remains the same size. The WAL is not truncated.

2.  **FULL:**
    *   Waits for all active readers to finish.
    *   Applies **all** changes from the WAL to the main database.
    *   **Crucial Distinction:** A FULL checkpoint does **NOT** truncate the WAL file size to zero. It ensures the main database file contains all committed changes, and the internal state is reset so the next writer can overwrite the beginning of the WAL file (starting from frame 0). The file size on disk remains unchanged until a TRUNCATE checkpoint is issued.
    *   **Blocking:** Blocks the writer until complete.

3.  **RESTART:**
    *   Behaves exactly like a FULL checkpoint.
    *   **Specific Use:** Primarily used in multi-process scenarios where a process needs to ensure the WAL is fully checkpointed and ready for reuse from the beginning, guaranteeing that no readers are holding references to old frames.
    *   **Effect:** Like FULL, it does **NOT** change the file size on disk.

4.  **TRUNCATE:**
    *   Added in SQLite 3.7.7.
    *   Performs a FULL checkpoint (waits for readers, applies all changes).
    *   **Additionally:** Truncates the WAL file size to **zero bytes** on disk.
    *   **Effect:** This is the only mode that physically shrinks the file size to zero on the filesystem. The next write will start a new WAL file instance (new salts/checkpoint sequence).

### 2.2 When Checkpointing Happens

Checkpointing is driven by:

1.  **Automatic Checkpointing:**
    *   SQLite automatically triggers a **PASSIVE** checkpoint when the WAL file grows to a certain size.
    *   **Default Threshold:** **1000 pages** (configurable via `PRAGMA wal_autocheckpoint`).
    *   **Behavior:** Because it is PASSIVE, if readers are active, the checkpoint may not complete. This means the WAL file can grow beyond 1000 pages if readers are long-lived. The auto-checkpoint runs after every transaction commit.

2.  **Explicit Checkpointing:**
    *   Via `PRAGMA wal_checkpoint[=mode]`.
    *   Used by applications to force synchronization or manage WAL file size (using TRUNCATE mode).

3.  **Transition Out of WAL Mode:**
    *   When `PRAGMA journal_mode=DELETE` (or TRUNCATE) is issued, a final FULL checkpoint is performed to apply all WAL changes to the main database. The `-wal` and `-shm` files are then deleted.

### 2.3 How Checkpointing Works Internally

The checkpoint process involves the following steps:
1.  **Lock Acquisition:** The process initiating the checkpoint acquires the necessary locks (Exclusive lock on the main DB file for FULL/RESTART/TRUNCATE; Shared/Exclusive coordination for PASSIVE).
2.  **Page Copying:** It reads frames from the WAL file and writes the page data to the corresponding page offsets in the main database file.
3.  **Header Updates:** It updates the main database file's header (e.g., the change counter, which is incremented to reflect the new state).
4.  **WAL Update:**
    *   For PASSIVE: The WAL is not modified. The "checkpointed" state is tracked internally.
    *   For FULL/RESTART: The WAL is logically reset. The next write will overwrite frame 0.
    *   For TRUNCATE: The WAL file is truncated to 0 bytes. The header is rewritten with new salts and an incremented checkpoint sequence number.

### 2.4 Concurrency During Checkpointing

*   **Readers:**
    *   Continue reading from their established snapshot.
    *   If a reader started *before* a checkpoint, it continues to read from the WAL frames corresponding to its snapshot.
    *   The WAL frames required by an active reader are never overwritten or deleted (in a TRUNCATE sense) until that reader commits or rolls back and releases its lock on the `-shm` file.

*   **Writers:**
    *   **PASSIVE:** Writers are not blocked. They continue writing to the WAL.
    *   **FULL/RESTART/TRUNCATE:** Writers are blocked until the checkpoint completes. This is because the checkpoint needs exclusive access to ensure all readers have finished and the state is consistent before resetting the WAL.

## 3. Concurrency Guarantees

WAL mode fundamentally changes the concurrency model of SQLite by separating reads from writes.

### 3.1 Isolation Level

SQLite operates at **Snapshot Isolation (SI)** in WAL mode.

*   **Snapshot Isolation:** Each reader sees a consistent snapshot of the database at the start of its transaction.
*   **Serializability:** While SQLite technically implements SI, it does **not** provide full SERIALIZABLE isolation guarantees by default.
    *   *Clarification:* In multi-writer systems, SI allows for "write-skew" anomalies. While SQLite enforces a **single writer** at the physical commit level (via the Exclusive Lock on the main database file), this does not automatically serialize *application-level logical transactions* unless the application holds the write lock for the duration of the logical transaction.
    *   *Example of Write-Skew in SQLite:* Two applications can open a transaction, read a value, compute a new value, and attempt to write it back. Because they are serialized at commit time, both might succeed in committing, resulting in a state that is not serializable (i.e., it cannot be achieved by any serial order of operations).
    *   *Achieving Serializability:* Applications must use `BEGIN IMMEDIATE` (which acquires the write lock at the start of the transaction) or explicit advisory locks to ensure that read-modify-write operations are atomic with respect to other transactions. Therefore, claiming SQLite WAL mode is "effectively SERIALIZABLE" without qualification is misleading. It is **Snapshot Isolated**, and serializability must be enforced by the application logic.

### 3.2 Reader/Writer Concurrency

*   **Multiple Readers:** Can read simultaneously while a writer is active. This is the primary advantage over rollback journal mode, where a writer locks the entire database, blocking readers.
*   **Single Writer:** Only one process can write at a time. Writers are serialized via the **Exclusive Lock on the main database file**.
*   **Readers and Writers:** Readers do not block writers. Writers do not block readers (except during FULL/RESTART/TRUNCATE checkpoints, which require readers to release their locks).

### 3.3 The Locking Protocol (WAL Specific)

The locking model in WAL mode is distinct from the rollback journal model.

1.  **Reader Access:**
    *   Readers **do not** acquire a Shared Lock on the main database file for normal reads in WAL mode.
    *   Instead, readers acquire a **read lock on the `-shm` file** (the WAL Index).
    *   This read lock ensures that the WAL file is not truncated or reset while the reader is accessing frames.
    *   Readers read page data directly from the WAL file if the page has been modified, or from the main database file if it hasn't.

2.  **Writer Access:**
    *   A writer **must** acquire an **Exclusive Lock on the main database file**. This is done via the standard transition: Shared -> Reserved -> Pending -> Exclusive.
    *   This Exclusive Lock on the main DB file serializes writers and prevents concurrent checkpoints that would interfere with the write.
    *   The writer also interacts with the WAL Index to append frames and update the `iFrame` counter.
    *   *Correction to Draft:* The claim that a writer "does not need to acquire a PENDING or EXCLUSIVE lock on the main database file" is **false**. It must hold the exclusive lock on the main DB file to ensure no other process is performing a checkpoint or reset. The WAL Index lock is secondary to this for writer serialization.

3.  **Deadlock Avoidance:**
    *   Deadlocks are avoided because:
        *   Readers only hold locks on the `-shm` file.
        *   Writers hold an exclusive lock on the main DB file and a lock on the WAL Index.
        *   There is no circular wait because readers do not block writers (writers ignore reader locks on `-shm` for the purpose of starting a write, but they *do* block if they need to reset the WAL, which requires readers to release `-shm` locks). However, standard reads do not prevent a writer from committing to the WAL.

### 3.4 Limitations

*   **WAL File Growth:** If readers are long-lived, the WAL file may grow large because PASSIVE checkpoints (the default auto-checkpoint) cannot complete. Applications must monitor WAL size or use TRUNCATE checkpoints explicitly.
*   **Network File Systems:** WAL mode is **not recommended** for use on network file systems (NFS, SMB) that do not provide strict, immediate lock visibility and atomic rename/append semantics. SQLite assumes local filesystem semantics. The `-shm` file, in particular, relies on efficient shared memory mapping or file locking, which can be problematic over networks.
*   **Read-Only Constraints:**
    *   A read-only connection **cannot** create a WAL file.
    *   If a read-only connection attempts to open a database that is in WAL mode, the `-wal` and `-shm` files must already exist and be readable.
    *   If the `-shm` file cannot be created (e.g., read-only filesystem for the directory) or if the `-wal` file is present but the `-shm` file is missing, the connection may fail. It cannot fall back to rollback journal mode safely if a WAL exists, as this would lead to inconsistency.

## 5. Gaps and Open Questions

1.  **Optimal WAL Autocheckpoint Setting:** The default of 1000 pages may not be optimal for all workloads. Empirical studies on this are scarce.
2.  **Shared Memory Portability:** On systems that do not support memory-mapped files, the `-shm` file falls back to a file-based shared memory mechanism, which can be slower. The impact on high-concurrency workloads is not widely documented.
3.  **Cryptographic Checksums:** The checksum used in WAL is a simple arithmetic checksum, not cryptographic. This is sufficient for corruption detection but not for integrity in adversarial environments.

---

## 6. Conclusion

SQLite's WAL mode provides a robust, high-concurrency alternative to the traditional rollback journal. Its key features are:

*   **Structure:** A separate WAL file with a 32-byte header and 24-byte frame headers, containing modified database pages. A critical **WAL Index** stored in the `-shm` file coordinates readers and writers.
*   **Checkpointing:** A process that applies WAL changes to the main database. **FULL** checkpoints apply changes but do not reduce file size; only **TRUNCATE** checkpoints reduce the WAL file size to zero.
*   **Concurrency:** Provides **Snapshot Isolation** (not automatic Serializability). The critical advantage is that **readers do not block writers**. Concurrency is managed via locks on the `-shm` file for readers and an **Exclusive Lock on the main database file** for writers.

This design makes WAL mode suitable for applications with mixed read/write workloads. The primary operational concern is managing WAL file size, requiring careful monitoring or explicit TRUNCATE checkpoints in scenarios with long-lived readers. Applications requiring serializable isolation must implement their own locking mechanisms (e.g., `BEGIN IMMEDIATE`).

**Confidence Level:** High. The findings are based on the official SQLite documentation and source code, with specific corrections applied to address common misconceptions about locking and isolation levels.
