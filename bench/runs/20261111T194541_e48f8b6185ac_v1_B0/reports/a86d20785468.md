# SQLite WAL Mode Internals: Structure, Checkpointing, and Concurrency

## 1. Executive Summary

Write-Ahead Logging (WAL) mode is an alternative transaction journaling mode for SQLite. Unlike the default rollback journal mode (where the database file is restored from a backup journal on failure), WAL mode records changes in a separate log file and applies them to the main database file asynchronously. This mode significantly improves concurrent read performance and provides different (but robust) concurrency guarantees.

This report details:
1.  **WAL File Structure:** The binary layout, frame format, and header checksums.
2.  **Checkpointing Mechanisms:** Trigger conditions (auto, manual, passive, truncating, full) and their interaction with the database.
3.  **Concurrency Guarantees:** Reader-Writer isolation, locking behavior, and consistency properties.

*Note: All descriptions below are derived from the official SQLite documentation and source code analysis (version 3.40+). Citations refer to the official SQLite documentation pages and the C source files `wal.c` and `btree.c` where relevant. I am confident these sources exist as they are the primary authoritative references for SQLite behavior.*

## 2. WAL File Structure

When WAL mode is enabled, SQLite creates a new file alongside the database file: `<database_name>-wal`. This file is binary, append-only, and has a fixed-size header followed by a series of fixed-size frames.

### 2.1 The WAL Header (32 Bytes)

The first 32 bytes of the WAL file are the **WAL Header**. This header is written by the first writer to acquire the exclusive lock when the WAL file is created or truncated.

| Offset | Size | Field | Description |
| :--- | :--- | :--- | :--- |
| 0 | 4 | Magic Number | `0x377f0682` (big-endian) or `0x377f0683` (little-endian). |
| 4 | 4 | File Format Version | Always 3007000. |
| 8 | 4 | Database Page Size | Must match the page size of the database file. |
| 12 | 4 | Checkpoint Sequence Number | A monotonic counter incremented on each checkpoint. |
| 16 | 4 | Salt-1 | Random 32-bit value used to validate integrity. |
| 20 | 4 | Salt-2 | Random 32-bit value used to validate integrity. |
| 24 | 4 | Checksum-1 | First 32-bit checksum of the first 24 bytes of the header. |
| 28 | 4 | Checksum-2 | Second 32-bit checksum of the first 24 bytes of the header. |

**Key Detail:** The checksums in the header are **not** cumulative. They only cover the first 24 bytes of the header. This allows a reader to quickly verify if the WAL file is valid before parsing frames.

### 2.2 The Frame Format (24 + PageSize bytes)

Each entry in the WAL is a **Frame**. A frame consists of a 24-byte frame header followed by the page content.

| Offset (within frame) | Size | Field | Description |
| :--- | :--- | :--- | :--- |
| 0 | 4 | Page Number | The 1-based page number in the database file being written. |
| 4 | 4 | For Commit? | If non-zero, this frame commits the transaction. The value indicates the type of commit (e.g., `1` for normal, `2` for sync-off). |
| 8 | 4 | Salt-1 | Must match Salt-1 in the WAL Header. |
| 12 | 4 | Salt-2 | Must match Salt-2 in the WAL Header. |
| 16 | 4 | Checksum-1 | First 32-bit checksum of the current frame header (24 bytes) + page data. |
| 20 | 4 | Checksum-2 | Second 32-bit checksum of the current frame header + page data. |
| 24 | PageSize | Page Data | The raw bytes of the database page being modified. |

**Cumulative Checksums:**
Unlike the header, the frame checksums are **cumulative**.
- `Frame N` Checksum-1 = `Checksum1(Header Bytes of Frame N) + Frame (N-1) Checksum-2`
- `Frame N` Checksum-2 = `Checksum2(Header Bytes of Frame N) + Frame (N-1) Checksum-2`

This chain ensures data integrity across the entire log. If any byte in any previous frame is corrupted, the checksum for subsequent frames will fail. Readers use this to determine the **safe boundary** of valid frames (the "last valid frame").

### 2.3 The WAL File Lifecycle

1.  **Creation:** When the first writer begins a transaction in WAL mode, SQLite creates the `-wal` file and writes the 32-byte header.
2.  **Appends:** As the writer modifies pages, those pages are appended as frames to the WAL file. The `write` system call is used; SQLite does not rewrite earlier parts of the WAL file.
3.  **Truncation:** When a checkpoint occurs (see Section 3), the WAL file may be truncated or renamed, but it is never deleted while any connections are open.

## 3. Checkpointing Mechanisms

Checkpointing is the process of copying pages from the WAL file into the main database file (`<database_name>`). This is necessary to:
- Prevent the WAL file from growing indefinitely.
- Allow the database to be copied or backed up without the WAL.
- Enable rollback journal mode if the user switches modes.

### 3.1 Types of Checkpoints

SQLite defines four types of checkpoints, controlled by the `PRAGMA wal_checkpoint` command or internal logic:

| Type | Behavior | Lock Required | Use Case |
| :--- | :--- | :--- | :--- |
| **PASSIVE** | Copies pages to the DB file *if possible*. If a reader is currently using the WAL, it stops at the first page the reader needs. Does **not** truncate the WAL. | Shared Lock | Default internal checkpoint. Safe to run at any time. |
| **FULL** | Waits for readers to complete before copying all pages to the DB file. After copying, it truncates the WAL file to zero bytes (reusing the same inode). | Shared Lock (waits) | Ensures the DB file is up-to-date and the WAL is cleared. |
| **RESTART** | Same as FULL, but additionally resets the WAL file’s offset so the next writer starts from frame 0. | Shared Lock (waits) | Useful for long-running processes to prevent WAL bloat. |
| **TRUNCATE** | Same as RESTART, but also truncates the `-wal` file to zero bytes on disk (releases space). | Shared Lock (waits) | Best for minimizing disk usage. |

> **Source Confidence:** High. These definitions are explicitly documented in the SQLite PRAGMA documentation. The distinction between PASSIVE and FULL is critical for understanding why a "busy" error might not occur with PASSIVE checkpoints.

### 3.2 When Do Checkpoints Happen?

Checkpoints are triggered by three mechanisms:

#### A. Automatic Checkpoints (Default)
By default, SQLite triggers a **PASSIVE** checkpoint whenever a transaction commits **and** the WAL file contains more than `wal_autocheckpoint` pages (default: 1000 pages).
- **Calculation:** If the page size is 4096 bytes, the threshold is ~4 MB.
- **Behavior:** If a reader is active, the checkpoint stops at the reader's last read frame. The WAL continues to grow. If no readers are active, the WAL is truncated to zero.
- **Tunable:** `PRAGMA wal_autocheckpoint = 100;` changes the threshold. Set to `0` to disable.

#### B. Manual Checkpoints
The user can explicitly invoke:
```sql
PRAGMA wal_checkpoint(PASSIVE);
PRAGMA wal_checkpoint(FULL);
PRAGMA wal_checkpoint(RESTART);
PRAGMA wal_checkpoint(TRUNCATE);
```
These return a row: `(busy, log, checkpointed)` where:
- `busy`: 0 if all frames were copied, 1 if a reader prevented completion.
- `log`: Total frames in the WAL at start of checkpoint.
- `checkpointed`: Number of frames successfully copied to the DB.

#### C. On Shutdown
When the last connection to the database is closed, SQLite automatically performs a **TRUNCATE** checkpoint. This ensures the `-wal` file is cleared and the main database file is complete and consistent for external tools.

### 3.3 How Checkpointing Works Internally

1.  **Lock Acquisition:** The checkpointing thread acquires a **shared lock** on the WAL file. This does not block writers (who hold a shared lock during their write) but does block other checkpointers.
2.  **Frame Copying:** For each frame in the WAL (from the oldest to the newest):
    - The frame’s page number is read.
    - The page data is copied to the corresponding page in the main database file.
    - This is done using `memcpy` or `write` system calls.
3.  **WAL Header Update:** After copying, the `Checkpoint Sequence Number` in the WAL header is incremented.
4.  **Truncation (if FULL/RESTART/TRUNCATE):**
    - The WAL file is truncated to zero bytes (or its inode is reused for the next transaction).
    - The `Salt-1` and `Salt-2` values are reset to random values.
    - The `Checkpoint Sequence Number` is reset or incremented (implementation detail: it is incremented, and salts are regenerated on restart).

> **Methodological Note:** The checkpoint is **not atomic** with respect to the main database file. If the process crashes mid-checkpoint, the main database file may be in an inconsistent state (some pages updated, others not). However, this is **safe** because SQLite will detect the inconsistent state on next open and replay the WAL file to restore consistency. The WAL file is the source of truth until it is fully checkpointed and truncated.

## 4. Concurrency Guarantees

WAL mode fundamentally changes SQLite’s concurrency model compared to rollback journal mode.

### 4.1 Read-Write Concurrency

**Key Guarantee:** **Readers do not block Writers, and Writers do not block Readers.**

- In rollback journal mode, a writer acquires an **exclusive lock** on the database file, blocking all readers until the transaction commits or rolls back.
- In WAL mode, a writer acquires a **shared lock** on the WAL file (not the main DB file) while writing. Readers also acquire a shared lock on the WAL file. Since multiple shared locks can coexist, readers and writers can operate concurrently.

**Mechanism:**
- When a reader opens a transaction, it records the **last valid frame** it sees in the WAL (the "read snapshot").
- The reader reads pages from the **main database file** unless the page number is modified in the WAL up to its snapshot frame.
- Writers append new frames to the end of the WAL. They do not modify existing frames or the main database file directly.
- Thus, the reader sees a consistent snapshot of the database as it existed when it started its transaction, even as writers add new data.

> **Source Confidence:** High. This is the primary marketing and technical advantage of WAL mode, documented extensively in the SQLite "WAL Mode" and "Concurrency Control" documentation.

### 4.2 Writer-Writer Concurrency

**Key Guarantee:** **Only one writer can write to the database at a time.**

- While multiple readers can be active, only **one** writer can be active at a time.
- A second writer attempting to start a transaction will receive a `SQLITE_BUSY` error (or wait, if `busy_timeout` is set).
- This is because the first writer holds an **exclusive lock** on the WAL file’s **write** region (implemented via a dedicated write lock, not the main shared lock).

**Why not multiple writers?**
SQLite’s B-tree structure is not designed for concurrent page-level writes without complex locking. Allowing multiple writers would require row-level or page-level locking, which SQLite does not implement. WAL mode optimizes for **read-heavy, write-light** workloads.

> **Limitation:** This is a significant limitation compared to full-fledged RDBMSs like PostgreSQL or Oracle. For high-write concurrency, SQLite is not suitable, even in WAL mode.

### 4.3 Consistency Guarantees

- **ACID Compliance:** WAL mode fully adheres to ACID properties.
- **Isolation Level:** WAL mode provides **Snapshot Isolation** (readers see a consistent snapshot as of their transaction start).
- **Atomicity:** All changes in a transaction are either fully applied to the WAL and then checkpointed, or fully rolled back. A crash during write only affects the WAL, which is replayed on recovery.
- **Durability:** Changes are durable once `fsync()` is called on the WAL file (which SQLite does by default for each commit, unless `PRAGMA synchronous=OFF` is set).

> **Critical Note:** The `synchronous` pragma still applies in WAL mode. `synchronous=FULL` (default) ensures `fsync()` on the WAL file. `synchronous=NORMAL` fsyncs only once per checkpoint, not per commit. `synchronous=OFF` disables fsync, risking data loss on power failure.

### 4.4 Recovery and Consistency After Crash

1.  **Open Database:** SQLite opens the main database file and the WAL file.
2.  **Validate WAL:** It checks the WAL header and frame checksums to determine the last valid frame.
3.  **Replay:** It replays all valid frames from the WAL to the main database file (this is effectively a **FULL** checkpoint).
4.  **Truncate WAL:** After replay, the WAL file is truncated.
5.  **Result:** The database is in a consistent state, reflecting all committed transactions.

This process is fast because it only processes the WAL file, not the entire database.

## 5. Performance Implications

### 5.1 Advantages
- **Reduced I/O for Writes:** Writes are sequential appends to the WAL file, which are faster than random writes to the main database file.
- **Improved Concurrency:** Readers are not blocked, improving throughput in read-heavy applications.
- **Faster Checkpoints:** Passive checkpoints can occur in the background without blocking readers.

### 5.2 Disadvantages
- **WAL File Growth:** If readers are long-lived, the WAL file can grow large, consuming disk space.
- **Extra I/O for Checkpoints:** Checkpointing requires copying pages from WAL to DB, which is additional I/O.
- **Complexity:** Managing WAL files (especially in shared directories) can be complex in distributed systems.

> **Empirical Data:** While I do not have specific benchmark numbers from a single study, the SQLite documentation and community benchmarks consistently show that WAL mode can improve read concurrency by an order of magnitude compared to rollback journal mode. For write-heavy workloads, the difference is less pronounced, as the single-writer bottleneck remains.

## 6. Limitations and Open Questions

### 6.1 Limitations
1.  **Single Writer:** SQLite remains a single-writer system, even in WAL mode. This is a fundamental architectural limitation, not a WAL-specific one.
2.  **File System Requirements:** WAL mode requires the file system to support:
    - `ftruncate()` for truncating the WAL file.
    - `fcntl()` or `lockf()` for file locking.
    - Reliable `fsync()` semantics.
    - **Note:** WAL mode does **not** work on NFS or some network file systems that do not support POSIX locks or have inconsistent fsync semantics.
3.  **Memory Usage:** The WAL file must be kept in memory or on disk; large WAL files can consume significant memory if the operating system pages them in.

### 6.2 Open Questions / Gaps
1.  **Long-Running Readers:** What is the optimal strategy for applications with very long-running read transactions? Should the application periodically force a checkpoint to prevent WAL bloat?
2.  **Multi-Process vs. Multi-Thread:** WAL mode works for both, but the locking behavior is identical. There is no special optimization for multi-threaded in-process access vs. multi-process access.
3.  **Comparison with Other Systems:** How does SQLite WAL mode compare to PostgreSQL’s Write-Ahead Log in terms of throughput and latency? (This is outside the scope of SQLite internals but is a common practical question.)

## 7. Conclusion

SQLite WAL mode is a sophisticated, efficient mechanism for enabling concurrent reads while maintaining ACID compliance. Its binary WAL file structure, with cumulative checksums and frame-based logging, ensures data integrity and crash recovery. The checkpointing mechanism, with its multiple modes (PASSIVE, FULL, RESTART, TRUNCATE), provides flexibility for managing WAL file size and database consistency.

The key concurrency guarantee is **reader-writer concurrency**: readers are never blocked by writers, and vice versa. However, **writer-writer concurrency** is not supported, limiting SQLite to single-writer workloads.

For most applications, WAL mode is the preferred journaling mode due to its superior read concurrency and write performance. Users should be aware of the limitations regarding file system requirements and the single-writer bottleneck.
